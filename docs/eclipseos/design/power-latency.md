# Power and latency design

Status: proposed. The maintainer must accept this default through the orchestrator before it becomes an implementation requirement.

## Atlas today

Atlas offers a `disable-power-saving` option that runs its Power-saving control. Without that option, it activates the Balanced power scheme. The same task unconditionally disables Fast Startup; hibernation is a separate `disable-hibernation` option. The `.pow` file association imports a scheme when opened. ([Atlas performance map](../../map/tweaks-performance.md); `src/playbook/Configuration/tweaks/scripts/script-power.yml:5-32`; `src/playbook/Configuration/tweaks.yml:363`; `src/playbook/Configuration/tweaks/qol/explorer/import-power-plan.yml:2-23`)

Other Atlas performance actions set MMCSS `SystemResponsiveness` to 10, disable SleepStudy-related event channels and the Power Efficiency Diagnostics `AnalyzeSystem` task, set Windows Search to respect power modes, alter foreground scheduling, and disable selected service-host splitting. These are separate policy and diagnostic changes, not a single power profile. The cited performance group runs these actions without a build condition; its FTH changes are architecture-specific. ([Atlas performance map](../../map/tweaks-performance.md); `src/playbook/Configuration/tweaks.yml:40-66`; `src/playbook/Configuration/tweaks/performance/config-mmcss.yml:1-12`; `src/playbook/Configuration/tweaks/performance/disable-sleep-study.yml:1-14`; `src/playbook/Configuration/tweaks/performance/respect-power-modes-search.yml:1-9`; `src/playbook/Configuration/tweaks/performance/system/win32-priority-separation.yml:1-9`; `src/playbook/Configuration/tweaks/performance/system/disable-service-host-split.yml:1-14`)

Microsoft describes Balanced as adjusting performance and power use to demand, High Performance as prioritizing maximum performance at the expense of power, and notes that Modern Standby devices use Balanced or a plan derived from it. Microsoft documents MMCSS as scheduling time-sensitive multimedia work and describes `SystemResponsiveness` as the CPU percentage guaranteed to low-priority tasks; it does not claim that Atlas's value of 10 improves game frame times. ([Microsoft power policy settings](https://learn.microsoft.com/en-us/windows/win32/power/power-policy-settings); [Microsoft MMCSS documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service))

The inspected upgrade revert removes Explorer folder-description registry values and does not restore these power, scheduler, event-channel, or scheduled-task settings. The AtlasDesktop controls and the `.pow` import association do not by themselves establish a general rollback to the user's previous power configuration. (`src/playbook/Configuration/atlas/revert.yml:1-36`; [Atlas performance map](../../map/tweaks-performance.md))

## Lab evidence and limits

The two 26300 lab lanes record power scheme among the common performance probe fields, but the published lane summaries do not report its value. The comparison records process, service, task and memory counts; it does not report frame times, input latency, CPU frequency, temperatures, battery drain, or a controlled power-plan comparison. These runs therefore provide no evidence that a power tweak reduced latency or improved gaming performance. ([lab method](../lab/method.md); [lane A](../lab/lane-a.md); [lane B](../lab/lane-b.md); [lab comparison](../lab/comparison.md))

The 26H2 survey is a dated source review rather than matched performance testing, and does not establish which power profile or scheduler settings improve gaming performance. ([26H2 playbook survey](../research/26h2-playbooks.md); [survey scope and limits](../research/26h2-playbooks.md))

## Proposed EclipseOS default

1. **Keep the Windows and device-vendor power configuration by default.** Do not force High Performance, disable power-saving features globally, or import an opaque power plan on first install. Let Windows manage performance and energy use according to the active device and user mode. Make any higher-performance profile an explicit user choice with its effect on power, heat, fan noise and battery life stated.
2. **Preserve sleep, hibernation and Fast Startup choices.** Do not disable hibernation or change Fast Startup as a gaming default. If EclipseOS offers these settings, expose them separately from gaming performance, explain the storage and startup behavior, and allow the user to restore the previous values.
3. **Keep power-aware background behavior.** Retain Windows Search's power-mode behavior and do not disable power diagnostics or scheduled analysis by default. Offer diagnostic privacy controls separately, describing which logs and task are affected and how to restore them.
4. **Do not bundle scheduler tweaks as latency fixes.** Keep MMCSS, foreground scheduling and service-host behavior at Windows defaults unless a repeatable, device-specific test supports a particular change. Document exact values and scope; do not imply that MMCSS's low-priority CPU guarantee directly predicts game performance.
5. **Capture the actual starting profile and support rollback.** Record active scheme and relevant AC/DC settings before applying an optional profile. Show the changed settings, provide a restore action for the captured state, and verify scheme, sleep/wake, hibernation and battery behavior after reboot. Microsoft's `powercfg` tools can list and query schemes; use these records for review and recovery rather than assuming every device exposes the same schemes. ([Microsoft powercfg reference](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/powercfg-command-line-options))
6. **Require matched performance evidence.** Compare the stock and optional profiles on supported physical systems with the same BIOS, OS build, driver, game scene, resolution, frame cap, AC/battery state and ambient conditions. Record frame-time distributions (including 1% lows), CPU/GPU clocks and temperatures, power draw, and idle behavior. Repeat runs, report variation, test sleep/wake and peripherals, then restore and repeat the baseline. VM process or task counts are not latency measurements.

## Trade-offs and acceptance checks

Keeping Windows power management can allow lower clocks or background throttling when the device is idle or on battery; forcing a higher-performance mode can raise energy use, heat and noise without improving a particular game's frame times. Retaining diagnostics uses storage but preserves information useful for troubleshooting. The proposed default favors device-aware behavior, user choice and rollback over an unmeasured global optimization.

For every supported device class, test the default and each offered profile on AC and battery where applicable. Record the original and resulting power configuration, repeated game frame-time measurements, temperatures and power draw, idle consumption, sleep/wake and hibernation behavior, then verify rollback after reboot. Check audio and controller behavior under load. A profile is not ready to ship if it lacks a visible restore path or if its claimed benefit is smaller than the observed run-to-run variation.
